# みらい議会＠遠賀町 設計ドラフト v0.3

最終更新: 2026-09-22

---

## 1. 目的

1. 遠賀町議会の議事を、町民がわかりやすく把握できるようにする。
2. 各議員と町（町長・執行部）のやりとり、特に**誰がどんな発言をしたか**がすぐにわかるようにする。
3. 議案ごとに、質疑・討論・議決結果をひとつのページで追えるようにする。

## 2. 決定事項

| 項目 | 決定内容 |
|---|---|
| 構成 | プランB：静的サイト＋データ生成パイプライン |
| ホスティング | エックスサーバー（静的ファイルのみ） |
| URL | `https://miraigikai.onga-mirai-tech.com`（サブドメイン、無料SSL） |
| 立場 | 個人の非公式サイト |
| 対象期間 | **令和元年（2019年5月）以降のみ**。平成31年以前は取得も公開もしない（2026-09-23 変更。令和分で情報量として足りるという判断）。既に取得済みの平成分303日程は data リポジトリに残すが、サイトには載せない |
| 対象会議 | **定例会と臨時会の両方**を対象とする（本会議のみ。委員会の会議録は公開されていない）。全期間で定例会375日程＋臨時会約85日程 |
| 議案 | 扱う |
| 委員会 | 委員会での審議内容は**扱わない**（常任委員会の会議録は公開されていない。P0で確認）。ただし**付託の状態は議案ごとに表示する**（委員会名つき／付託省略／未付託の3状態。「6. 画面構成とURL → 委員会付託の表示」参照） |
| 議決結果の取得元 | **会議録本文から抽出する**。町HPの「審議案件・結果」PDFは本文の取得元にはせず、**verify工程の照合材料として使う** |
| 一般質問通告書 | **使う**。町HPのPDF（平成19年〜）から質問事項・要旨・質問の相手を取得し、要約の単位の正解データにする |
| 要約の粒度 | 一般質問は**質問事項ごと**、議案は**質疑または討論があったものだけ**。会議・定例会のまとめは**AIを使わず機械的に組み立てる**（「7. AI要約の方針 → 要約の単位」参照） |
| 依存ライブラリ | **2つだけ許容する**。`pypdf` — 一般質問通告書が会議録から復元できない情報を持ち、代替手段がないため。`anthropic` — Batch API のバッチ作成・状態確認・結果JSONLの取得と、混雑時の再試行を公式実装に任せるため（2026-09-23 決定）。要約は一度しか生成しない方針なので、取りこぼしにくい実装を優先した。それ以外は引き続き最小限にする |
| リポジトリ構成 | **コードは public、取得した原文とその派生物は private の別リポジトリ**に分ける（「3. 全体構成 → リポジトリ構成」参照）。議会事務局の了解が取れたらデータ側も public に切り替える |
| AIチャット | 実装しない |
| AI要約 | Claude API（Batch API）でビルド時に生成・保存 |
| 議員の顔写真 | 扱わない |
| 更新頻度 | GitHub Actions で**毎月1回**確認（手動実行も可） |
| 公開フロー | 半自動（PR作成 → プレビュー確認 → マージで本番反映） |

## 3. 全体構成

```
[VOICES 会議録システム] ──(月1回・低頻度取得)──▶ [GitHub Actions]
                                                   │
      ① 取得 fetch        data/raw/        原文HTMLを保存
      ② 整形 parse        data/normalized/ 会議・発言・議案をJSON化
      ③ 要約 summarize    data/summaries/  Claude Batch API
      ④ 検証 verify       数字・固有名詞の照合、スキーマ検証
      ⑤ 生成 build        dist/            静的HTML・検索インデックス
                                                   │
                         PR作成 ─▶ プレビュー確認 ─▶ マージ
                                                   │
                                        SFTP ─▶ [エックスサーバー]
```

### リポジトリ構成

| リポジトリ | 公開 | 中身 |
|---|---|---|
| `Onga-Mirai-Tech/Onga-Mirai-Gikai` | **public** | `pipeline/` `site/` `docs/` `masters/` `state.json` |
| `Onga-Mirai-Tech/Onga-Mirai-Gikai-data` | **private**（当面） | `raw/` `normalized/` `summaries/` |

data リポジトリは、コード側の **`data/` にまるごと checkout する**（`data/` は `.gitignore`）。
`masters/` と `state.json` を `data/` の外に置いているのは、`data/` を丸ごとdataリポジトリに明け渡して衝突をなくすため。

```yaml
- uses: actions/checkout@v4
- uses: actions/checkout@v4
  with:
    repository: Onga-Mirai-Tech/Onga-Mirai-Gikai-data
    path: data
    ssh-key: ${{ secrets.DATA_REPO_DEPLOY_KEY }}
```

分ける理由:

- 取得した原文は町・議会の著作物で、遠賀町公式サイトの著作権方針は「著作権法で認められた場合を除き、無断で複製・転用することはできません」としている（ https://www.town.onga.lg.jp/site/userguide/5959.html ）。public リポジトリに置くことは再配布にあたりうる。
- 一方、**OSSとしての価値はコード側にある**。VOICES は全国の議会で使われている会議録システムなので、このパイプラインは他の自治体にそのまま転用できる。そこは最初から完全に公開する。
- `state.json`（取得済みURLとハッシュの一覧）は public 側に置く。**第三者が自分で取得すれば同じ結果に到達できる**状態を保つため。
- `masters/`（発言者マスタ）は事実データなので public 側に置く。

運用:

- GitHub Actions は deploy key で data リポジトリを checkout する。
- **P3（閲覧MVP）完成 → 議会事務局へ連絡 → 了解が取れたら data リポジトリを public に切り替える。** 了解が取れなくてもコードは公開されたままで、OSSとしての価値は損なわれない。
- `normalized/` は `raw/` からローカル計算で再生成できるが、`summaries/` は「一度生成したら再生成しない」ルールがあるため**確実に永続化する**（CIのキャッシュでは要件を満たさない）。

## 4. データソース

### 4-1. 会議録（VOICES）

- トップ: `http://iasb-sv.town.onga.lg.jp/voices/index.asp`
- 年度・種別ごとの一覧は `index.asp?Sflg=11&FYY=YYYY&TYY=YYYY`（定例会）、`Sflg=21`（臨時会）。
- 一覧本体は `cgi/voiweb.exe?ACT=100&...` をフレーム内で表示する構成。
- 収録範囲: 平成17年（2005）〜 令和8年（2026）の定例会・臨時会。
- **P0で確認すること**
  - 文字コード（Shift_JIS の可能性が高い）
  - 会議録本文ページのURL規則と、1日分・1会議分の単位
  - 発言者の表記ルール（例：「○議長（氏名君）」「○○番（氏名君）」「○町長（氏名君）」など）
  - 発言区切りの記号、ト書き（「〔拍手〕」「起立多数」など）の表記
  - 目次・出席者一覧・議事日程の位置と形式
  - 委員会の会議録が含まれるか
  - 平成17年頃と令和の会議録で形式に差があるか
  - https 対応の有無（http のみならパイプライン側で取得するだけなので問題なし）

### 4-2. 議案・議決結果

- 会議録内の「議案第○号」の上程・質疑・討論・採決の流れから抽出する。定型文で進むため機械的に追える（P0で確認済み）。
- 町HPにも「審議案件・結果」の一覧がある（**PDFのみ**、1会議1ファイル、テキストレイヤあり）。議決結果は会議録本文だけで取れるので**本文の取得元にはしない**が、`議案番号 / 件名 / 議決年月日 / 議決結果` が独立した第二の情報源になるため、**verify工程で会議録から抽出した結果と突き合わせる**。食い違ったらビルドを止めて人が確認する。
- 議案の上程日と採決日は別の日程にまたがるため、**同一定例会内の複数日程をまたいで1議案の流れを組み立てる**必要がある。
- **個人別賛否は公表されていない**（P0で確認）。会議録の起立採決は `───　賛成者起立　───　１１：１〔１３〕` という賛否の人数のみ、異議なし採決は人数すら出ない。町HPのPDFも議決結果のみ。よって**個人別賛否は扱わない**。表示は「議決結果」と、起立採決の場合の「賛否の人数」までとする。
- 議案が常任委員会に付託された場合、**委員会の会議録はHPに公開されていない**（VOICES・町HP議会ページ・議会だよりの3か所を確認済み。なお委員会自体は傍聴できる）。付託の事実と委員会名は会議録本文から取れるので、議案ごとに状態を表示して空白になる区間を明示する（表示文言は「6. 画面構成とURL → 委員会付託の表示」）。
- 付託先の委員会名は本会議の会議録にそのまま書かれている（`第一常任委員会` / `第二常任委員会`、所管ごとに両方へ分割付託されることもある）。
- 委員長報告が本会議の会議録に含まれるかは **P2 で確認する**（含まれる見込み。含まれるなら議案ページから原文へリンクできる）。

### 4-3. 一般質問通告書

- 出典: 遠賀町公式サイト「一般質問通告書」 https://www.town.onga.lg.jp/site/gikai/list20-62.html
- 町HPには**平成17年〜令和8年**の通告書がある（VOICESの収録範囲と完全に一致する）。ただし**取得も利用も令和元年以降だけ**にする（2026-09-23 の対象期間の変更に合わせる）。定例会ごとに1PDF、年3〜4件。
- 中身は表形式で `通告順 / 質問者 / 質問事項（大項目） / 質問の要旨 / 質問の相手` が取れる。テキストレイヤがあり解析できる。
- **これは会議録から復元できない情報**で、一般質問の要約を「質問事項ごと」に切るための**正解データ**として使う（「7. AI要約の方針 → 要約の単位」参照）。
- 取得はページIDが分かっているURLだけを直接叩く（年別ページ20件＋PDF約70件）。探索はしない。間隔を空けるのはVOICESと同じ。
- 対象期間（令和元年〜）は通告書がそろっているため、質問事項の切り分けを会議録本文だけで行う必要はない。

### 4-4. 議員情報

- 氏名・会派・在任期間を町HP等の公開情報から手動で `data/masters/` に登録する。
- 顔写真は扱わない。

## 5. データモデル

IDは読みやすく安定したものにする。

### Meeting（会議）
```json
{
  "id": "2025-t3",
  "type": "定例会",            // 定例会 | 臨時会
  "year": 2025,
  "era_label": "令和7年",
  "number": 3,
  "title": "令和7年第3回定例会",
  "days": [
    { "day": 1, "date": "2025-09-02", "source_url": "http://iasb-sv..." }
  ],
  "agenda": ["開会", "議案上程", "一般質問", "..."]
}
```

### Speaker（発言者）
```json
{
  "id": "sp-yamada-taro",
  "name": "山田 太郎",
  "kind": "議員",               // 議員 | 町長 | 副町長 | 教育長 | 執行部 | 議長 | その他
  "roles": [
    { "title": "議員", "faction": "〇〇会", "from": "2019-05-01", "to": null }
  ],
  "aliases": ["山田太郎君", "山田議員"]
}
```
- 執行部（課長など）は年度で役職が変わるため、`roles` に履歴を持つ。
- 表記ゆれは `aliases` で吸収する。自動判定できなかったものは一覧に出して手動で登録する。

### Utterance（発言）
```json
{
  "id": "2025-t3-d2-0045",
  "meeting_id": "2025-t3",
  "day": 2,
  "seq": 45,
  "speaker_id": "sp-yamada-taro",
  "role_at_time": "議員",
  "text": "（原文）",
  "section": "一般質問",        // 議事の区分
  "thread_id": "2025-t3-q05",   // 一般質問の場合
  "bill_ids": [],               // 議案の質疑・討論の場合
  "source_url": "http://iasb-sv..."
}
```

### Thread（一般質問のやりとり）★中核
```json
{
  "id": "2025-t3-q05",
  "meeting_id": "2025-t3",
  "questioner_id": "sp-yamada-taro",
  "order": 1,                    // 通告順
  "topics": [
    {
      "no": 1,                                  // 通告書の質問事項の番号
      "title": "通学路の安全対策について",         // 通告書の質問事項（大項目）そのまま
      "points": ["⑴ 通学路の危険箇所の把握状況を尋ねる。", "⑵ …"],  // 通告書の質問の要旨
      "responder": "町長",                       // 通告書の「質問の相手」
      "summary_id": "2025-t3-q05-t1"            // この単位で要約を作る
    }
  ],
  "responders": ["sp-choucho", "sp-kyouikuchou"],
  "utterance_ids": ["2025-t3-d2-0045", "..."],
  "tags": ["教育", "防災"]
}
```
- 1人の議員の一般質問を1スレッドとし、**質問事項（通告書の大項目）ごとに `topics` の要素を作る**。
- `topics` の中身は**一般質問通告書（4-3）から取る**。議員自身の言葉なので、こちらで言い換えない。
- **要約は `topics` の1要素につき1つ**作る（スレッド全体で1つにはしない）。1人が無関係な4テーマを質問することが普通にあるため。
- 画面では「質問 → 答弁 → 再質問 → 再答弁…」の往復として表示する。

### Bill（議案）
```json
{
  "id": "2025-t3-b12",
  "meeting_id": "2025-t3",
  "number": "議案第12号",
  "title": "遠賀町〇〇条例の一部を改正する条例の制定について",
  "category": "条例",           // 条例 | 予算 | 決算 | 人事 | 契約 | 意見書 | 請願 | 報告 | その他
  "proposer": "町長",
  "submitted_on": "2025-09-02",
  "decided_on": "2025-09-19",
  "result": "原案可決",
  "vote_note": "起立多数",       // 会議録の記載そのまま
  "vote_count": { "yes": 11, "no": 1, "present": 13 },  // 起立採決のときのみ。なければ null
  "individual_votes": null,      // 常に null（公表されていない。下記参照）
  "referral": {
    "status": "committee",       // committee（付託あり）| omitted（付託省略）| none（付託の記載なし）
    "committees": ["第一常任委員会"],   // status=committee のとき。分割付託は複数入る
    "referred_on": "2025-09-05",
    "report_utterance_id": null  // 委員長報告の発言（P2で取得可否を確認）
  },
  "utterance_ids": []            // 質疑・討論の発言
}
```
- `individual_votes` は**常に null**。議員個人の賛否は会議録にも町の公表資料にも記載がない（P0で確認）。フィールドは将来公表された場合に備えて残すだけで、**推測して埋めることは絶対にしない**。
- `vote_count` は会議録の `───　賛成者起立　───　１１：１〔１３〕` から取る。異議なし採決では人数が出ないので null。

### Summary（AI要約）
```json
{
  "target_type": "thread",       // meeting | thread | bill | utterance
  "target_id": "2025-t3-q05",
  "summary": "（要約本文）",
  "points": [
    { "who": "sp-yamada-taro", "text": "（質問の要点）", "utterance_id": "..." },
    { "who": "sp-choucho", "text": "（答弁の要点）", "utterance_id": "..." }
  ],
  "model": "claude-...",
  "prompt_version": "thread-v1",
  "generated_at": "2026-10-01T02:00:00+09:00",
  "verified": true
}
```
- `points` の各要点は必ず元の発言IDに紐付け、画面から原文へ飛べるようにする。

## 6. 画面構成とURL

| URL | 画面 | 内容 |
|---|---|---|
| `/` | トップ | 最新の定例会サマリ、主な一般質問、最近の議案 |
| `/meetings/` | 会議一覧 | 年度・種別で絞り込み |

| `/bills/` | 議案一覧 | 種別・結果・年度で絞り込み |
| `/bills/{id}/` | 議案ページ | 概要、質疑・討論の発言、議決結果 |
| `/members/` | 議員一覧 | 現職・元職 |

### 委員会付託の表示

議案ページに、付託の状態を1行で必ず表示する。会議録に書かれている事実だけを出し、委員会で何が議論されたかには踏み込まない。

| `referral.status` | 表示文言 |
|---|---|
| `committee`（単一） | この議案は**第一常任委員会**に付託されました。委員会の会議録はHPに公開されていません。 |
| `committee`（分割） | この議案は所管ごとに**第一・第二常任委員会**に付託されました。委員会の会議録はHPに公開されていません。 |

| `none` | （表示しない） |

- 委員会名は会議録の文言をそのまま使う。こちらで言い換えたり省略したりしない。

### デザイン方針

画面デザインのたたき台は [`site/mockup/index.html`](../site/mockup/index.html)。町民に親しんでもらうことと、中立性を崩さないことの両立が主題。

- **やわらかさは色数ではなく形で出す。** 角の丸み・余白・やわらかい影で親しみを作り、**意味を持つ色は1色だけ**に保つ。禁じられているのは「可否や賛否に色を割り当てること」であって、サイト全体が温かい色であることではない。
- **配色は遠賀町公式ホームページに合わせた青系。** 公式サイトの実測値は 濃紺 `#17357D` / リンク青 `#0D59B7` / 淡い水色地 `#E9F5F9`。本サイトのアクセントは `#1F5FA8`、地色は `#F3F8FC`、淡地は `#E4EFF9`。
- **明るい配色に一本化する**（2026-09-23 決定）。端末が暗い設定でもこの配色で表示する。会議録は長文を続けて読むものなので、暗い背景では読みにくいという判断。そのため背景と文字色は必ず明示する。
- **色を公式サイトに寄せた分、区別は言葉で付ける。** 全画面のヘッダー右上に「非公式」ラベルを常時表示し、フッターに下記の注記を置く。色による見分けに頼らない。
- **書体で出どころを示す。** 丸ゴシック＝このサイトの言葉、明朝＝会議録や通告書の原文、点線の枠＋赤しそ地＝AIが書いたもの。ラベルを読まなくても3つを見分けられる。端末が持つフォントだけで組む（外部CDN不使用のため）。
- **発言者の記号は会議録のものをそのまま使う。** `○`議長 `◆`質問者 `◎`答弁者。検索システムの発言者区分と一対一で対応しており、こちらの解釈が混ざらない。
- **数は出すが、順位はつけない。** 質問件数は事実なので出す。ただし議員を並べた順位表は作らず、グラフの棒はすべて同じ色にし、「多い少ないが充実を表すわけではない」と画面に書き添える。
- **ロゴはC案「川と芽」に決定**（2026-09-22）。遠賀川の流れから芽が伸びる形。インラインSVGの単色図案で、文字色に追従する。基本形・反転（濃紺地、OGP用）・図案のみ小サイズ（ファビコン用、16px前後では2本目の波と左の葉を落として線を太くする）の3つを用意する。

### 議員ページの作り

**このサイトの中核機能のひとつ**として作る。ただし次の形を守る。

- **索引に徹する。** 質問事項の一覧・件数・議案での発言を、すべて各ページへの**リンクとして**並べる。発言そのものや要約の本文は議員ページに置かない。
- **議員から町長になった人も載せるが、載せるのは議員だったときの発言だけ**（2026-09-23 決定）。町長・執行部としての答弁は量が膨大で、索引として使えなくなる。議長・副議長・委員長は議員が務めるので含める。
- **現職かどうかは、いちばん新しい会議の出欠表に載っているかで判定する。** 日付からの当て推量をしない。見出しは「現職議員」「過去の議員」。

- **質問件数はその議員のページの中だけで示し、議員間で並べた順位表は作らない。** 画面に「回数の多い少ないは、議員の仕事ぶりを表すものではありません」と書く。

- 賛否は個人別に公表されていないため扱わない。「扱っていない」ことを画面に書く。

## 7. AI要約の方針

### 要約の単位

要約は**3つの単位でだけ**作る。会議・定例会のまとめはAIを使わない。

| 単位 | 作るか | 入力 | 出力 | ID（安定キー） |
|---|---|---|---|---|
| 一般質問の**質問事項ごと** | ○ | **その議員の往復全文**＋通告書のその議員の質問事項一覧 | 質問事項ごとの要約を**まとめて配列で**受け取る。**通告書の項目と1対1**に固定し、小問（(1)(2)(3)）や再質問はその項目の中の配列に入れる（2026-09-23） | `{meeting}-q{通告順}-t{質問事項番号}` |
| **議案ごと**（質疑または討論があったものだけ） | ○ | その議案の質疑・討論の発言（日程をまたぐ場合は全部） | 要約1つ | `{meeting}-b{議案番号}` |
| 質疑も討論もない議案 | ✕ | — | — | — |
| 1日程まるごと / 定例会まとめ | ✕ | — | — | — |

**入力の単位と出力の単位を分ける。** 一般質問は議員単位でまとめて投入し、質問事項ごとに分けて出力させる。理由:

- 再質問がテーマをまたぐことがあるため、テーマで切ってから投げると文脈が切れる。
- 通告書が質問事項の一覧と境界の正解を与えるので、**本文からテーマの切れ目を機械判定する必要がない**。

**会議・定例会のまとめにAIを使わない理由:**

- **正確性** — 要約の要約は原文から2段離れ、誤りが増幅する。CLAUDE.md の照合ルールと合わない。
- **「再生成しない」ルールと衝突する** — 会期中に最終日が追加されると内容が変わり、再生成が必要になる。質問事項単位・議案単位のキーは一度確定したら変わらない。

会議ページの概要は「一般質問 3人・9テーマ／議案 12件（原案可決10・承認2）」のように**下位の要約から機械的に組み立てる**。質疑も討論もない議案は「質疑・討論はありませんでした」と事実だけ書く。

### 使い方
- Claude API の **Batch API** で一括処理する（50%割引、即時性不要）。
- 生成済みの要約は再生成しない。プロンプト変更時のみ明示的に再生成する。
- モデルは **Sonnet 5**（`claude-sonnet-5`）。比較の経緯は「10. 未決事項」を参照。
- 出力は**ツール（JSON Schema）で受け取る**。地の文でJSONを書かせると前置きが混じる。
- 要約JSONに `PROMPT_VERSION` を記録する。再生成しない方針のため、どの版のプロンプトで作ったかが分からないと直せなくなる。

### 費用の考え方
- 従量課金。閲覧数には比例せず、**要約を生成するときだけ**費用が発生する。
- 初回一括（令和元年5月〜、157日程・実測252万字）は、全文を1回だけ投入した場合の上限で **入力 2.52M / 出力 0.32Mトークン**。Batch API（50%割引、2026-06-24時点の価格）で **Haiku 4.5 で約 $2.1、Sonnet 5 で約 $4.1**。全期間（460日程・987万字）でも **$7.9 / $15.9**。（P1の実測に基づく。`docs/調査報告_P0.md` の「4-2. P1実測との突き合わせ」参照）
- 上記は上限で、実際は出席者一覧・議事日程といった定型部分と、質疑も討論もない議案を投げないためさらに下がる。
- **費用はモデル選定の判断材料にならない。要約の品質と誤りの少なさで選ぶ**（P4で比較）。
- 平成分（P6）は取りやめたので、この費用は発生しない。
- Anthropic のコンソールで利用上限額を設定しておく。

### プロンプトの原則
- 発言者が言っていないことを補わない。推測・評価・感想を書かない。
- 数字・日付・固有名詞は原文どおりに書く。
- 答弁は「何をする／しない／検討する」という結論を明確にする。
- 要点ごとに根拠となる発言IDを出力させる（JSON形式）。

### 検証（verify）
- 要約中の数字・金額・日付・固有名詞が、紐付いた原文に含まれているかを機械的にチェックする。
- **議案の議決結果は、町HPの「審議案件・結果」PDF（4-2）と突き合わせる。** 会議録から抽出した `議案番号 / 議決年月日 / 議決結果` が一致しない議案を一覧に出す。独立した第二の情報源による照合なので、抽出ロジックの取りこぼしを拾える。
- **表記が食い違う議案は、どちらかに揃えず両方を原典のまま並べる**（2026-09-24決定）。「可決」と「認定」を同じ意味とみなして書き換えるのは、こちらの判断が入る行為で中立性の方針に反する。どちらも町が公開している公式資料であり、一方を誤りとみなす立場にない。画面には出どころ（会議録／審議案件・結果）を添え、「どちらが正しいかをこのサイトでは判断していない」と明記する。令和元年以降636件中8件が該当。
- 一般質問の質問事項が、通告書（4-3）の項目数と一致しているかを確認する。数が合わない場合は切り分けを誤った可能性がある。
- 不一致があれば `verified: false` にして PR 上で一覧表示し、人が確認する。

## 8. 更新・公開フロー

### 月次更新（monthly-update.yml）
- 実行: **毎月2日 日本時間の深夜**（cron は UTC 表記のため時差に注意）＋手動実行（workflow_dispatch）。
- 処理: VOICES の一覧を確認 → 未取得の会議録を取得 → 整形 → **要約を Batch API に投入する（回収はしない）** → dataリポジトリへ push。
- 投入したら `data/.update-in-flight` を置く。これが回収側への引き継ぎになる。

### 回収と公開の準備（summarize-collect.yml）
- 実行: **3時間おき**＋手動実行。`data/.update-in-flight` があるときだけ動く。
- **月次更新と分けている理由**: Batch API の完了までが読めない。実測で議案152件が4分、一般質問48件が11時間。GitHub Actions の1ジョブは6時間で切れるので、待ち続ける作りにできない。
- 処理: 要約を回収 → 未生成が残っていれば何もせず次回へ → 検証 → ビルド → プレビュー（Basic認証付き）へ反映 → **Pull Request を作成** → `.update-in-flight` を消す。
- 途中で落ちても、保存していない要約は次回また投げられる。二重に課金されない。
- 新しい会議録がない月も `state.json` の最終確認日時を更新してコミットする。
  - GitHub は60日間更新のないリポジトリの定期実行を自動停止するため、その対策。

### 本番デプロイ（deploy.yml）
- main への push（PRのマージ）をきっかけに、ビルドして SFTP でエックスサーバーの公開ディレクトリへ反映する。
- エックスサーバーの認証情報（Secrets）が未設定の間は、ビルドだけ行って終わる。
- `.htaccess` `.htpasswd` は同期から除く。サーバー側の設定（常時SSL化・Basic認証）の実体であり、消すと認証が外れる。

| 名前 | 用途 |
|---|---|
| `ANTHROPIC_API_KEY` | AI要約 |
| `XSERVER_HOST` / `XSERVER_USER` / `XSERVER_SSH_KEY` | SFTPデプロイ |
| `XSERVER_PUBLIC_DIR` / `XSERVER_PREVIEW_DIR` | デプロイ先 |
