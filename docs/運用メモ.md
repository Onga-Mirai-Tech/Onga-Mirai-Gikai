## 1. リポジトリ

| リポジトリ | 公開 | 中身 |
|---|---|---|
| [Onga-Mirai-Gikai](https://github.com/Onga-Mirai-Tech/Onga-Mirai-Gikai) | public | コード・ドキュメント・`masters/`・`state.json` |
| [Onga-Mirai-Gikai-data](https://github.com/Onga-Mirai-Tech/Onga-Mirai-Gikai-data) | **private** | `raw/`・`normalized/`・`summaries/` |

分ける理由は設計ドラフト「3. 全体構成 → リポジトリ構成」を参照。

### deploy key の設定（月次ワークフローに必要）

`.github/workflows/monthly-fetch.yml` が data リポジトリを checkout するために使う。

```bash
# 1. 鍵を作る（パスフレーズなし）
ssh-keygen -t ed25519 -C "onga-mirai-gikai-data-deploy" -f ~/.ssh/onga_data_deploy -N ""

# 2. 公開鍵を data リポジトリの Deploy keys に登録する（書き込みを許可する）
gh repo deploy-key add ~/.ssh/onga_data_deploy.pub \
  --repo Onga-Mirai-Tech/Onga-Mirai-Gikai-data --title "monthly-fetch" --allow-write

# 3. 秘密鍵を コード側リポジトリの Secrets に入れる
gh secret set DATA_REPO_DEPLOY_KEY \
  --repo Onga-Mirai-Tech/Onga-Mirai-Gikai < ~/.ssh/onga_data_deploy
```

秘密鍵はローカルに置いたままにせず、登録後に消してよい。

### 公開前に残っていること

1. **http → https の常時リダイレクト。** いま `http://` でアクセスすると、リダイレクトせず
   そのまま 200 が返る。エックスサーバーの「常時SSL化」設定か `.htaccess` で有効にする。
   静的ファイルしか置かない方針だが、リダイレクトはサーバー設定であって
   実行時のサーバー処理ではないので、CLAUDE.md の方針とは矛盾しない。
2. **既定ページの `noindex` を引き継がない。** いま出ているエックスサーバーの既定ページには
   検索避けの指定が入っている。本番のHTMLで上書きされるので自然に解消するが、
   公開直後に一度確認する。

状態はいつでもこれで確認できる。

```bash
d=miraigikai.onga-mirai-tech.com
curl -sS -o /dev/null -L -w 'http最終URL: %{url_effective} / リダイレクト %{num_redirects}回\n' "http://$d/"
echo | openssl s_client -servername $d -connect $d:443 2>/dev/null | openssl x509 -noout -subject -dates
```

`onga-mirai-tech.com` 本体（親ドメイン）は **Onga-Mirai-Tech のサイト**として使う。
みらい議会以外のサービスも展開していくため、サービスはそれぞれサブドメインに置く。

## 3. 連絡先メール

使いどころが3つある。どれも「個人運営の非公式サイト」として矛盾しない形にする。

1. **サイトの問い合わせ先**（フッター・aboutページ）
2. **訂正の受付**（要約や抽出の誤りの指摘）
3. **User-Agent に入れる連絡先** — いまは GitHub リポジトリのURLを入れている（`pipeline/common/http.py`）。町の担当者がアクセスログを見たときに辿れるようにするためのもの。サイト公開後は問い合わせページのURLに差し替えるか検討する

Onga-Mirai-Tech は、みらい議会以外のサービスも展開していく組織として運用する。

| アドレス | 用途 | 公開 | 状態 |
|---|---|---|---|
| `info@onga-mirai-tech.com` | Onga-Mirai-Tech 全体の問い合わせ窓口。みらい議会の問い合わせ・訂正の受付・議会事務局とのやりとりもここで受ける | する | **作成済**（2026-09-22） |
| `[管理用アドレス]` | GitHub・ドメイン・サーバーの管理 | **しない** | **作成済**（2026-09-22） |

- 迷惑メール対策は**エックスサーバーの迷惑メールフィルタで行う**（2026-09-22 決定）。
  アドレス名を読みにくくする工夫はしない。
- **キャッチオールは無効にしておく。** 存在しないアドレス宛を全部受け取る設定が有効だと、
  辞書攻撃がそのまま通ってフィルタの負荷にもなる。
- **管理用（`[管理用アドレス]`）は公開しない。** 公開側が迷惑メールで溢れても、ドメインやGitHubの
  復旧メールが埋もれない。
- **管理用の迷惑メールフィルタは緩めにしておく。** ここに来るのはアカウント復旧・
  証明書の期限通知・GitHubの通知など、**届かないと困るもの**ばかり。
  強いフィルタで復旧メールが迷惑メール扱いになると本末転倒になる。
  GitHub・エックスサーバー・レジストラの送信元を受信許可に入れておく。
- サービスが増えて振り分けが要るようになったら、`miraigikai@` のような
  **サービスごとのアドレスを後から足せる**。いまは窓口を1つにしておく。
- **GitHub Issues も窓口として併用できる**が、町民がGitHubアカウントを持っているとは
  限らないので、一般向けの窓口の代わりにはならない。技術的な指摘の受け皿として使う。

User-Agent に入れる連絡先（`pipeline/common/http.py`）は、いまは GitHub リポジトリのURL。
町の担当者がアクセスログを見たときに辿れるようにするためのもの。サイト公開後に
問い合わせページのURLへ差し替えるか検討する。

## 4. X アカウント

**Onga-Mirai-Tech の組織アカウント**として運用する。みらい議会だけでなく、
今後のサービスの告知にも使う。

**アカウント: [@OngaMiraiTech](https://x.com/OngaMiraiTech)**（2026-09-22 作成）。

### 名前と説明

- **「遠賀町の関連組織」と誤解されないようにする。** 組織名に「遠賀（Onga）」が入っているため、
  町の公式な部門だと読まれる余地がある。プロフィールに**個人が運営している旨**を書く。
- サービスごとの「非公式」の断りは、**プロフィールではなく個々の投稿とリンク先**で行う。
  組織アカウントなので、プロフィールに特定サービスの注記を書くと後で合わなくなる。
  みらい議会について投稿するときは、毎回リンク先（サイト）に非公式の明記がある状態にする。

### 投稿の方針

- **みらい議会に関する投稿には、CLAUDE.md の中立性ルールがそのまま及ぶ。**
  議員・会派・町への評価、点数付け、ランキング、賛否への言及をしない。
  告知は「更新しました」「この定例会を追加しました」に留める。
  他のサービスの投稿はこの制約の対象外だが、同じアカウントから出る以上、
  議会に関する話題では同じ姿勢を保つ。
- 議会に関する発信は政治的な反応を呼びやすい。**リプライの範囲を絞る**設定を
  最初から入れておくか決める。

### 見た目

- アイコン・ヘッダーは **Onga-Mirai-Tech のもの**。みらい議会のロゴ（C案）は
  みらい議会の告知に使うのであって、アカウントの顔には使わない。

## 5. 議会事務局への連絡

**P4（AI要約）の完成時**に行うと決めた（設計ドラフト「10. 未決事項」）。
当初はP3完成時としていたが、下の2つめが著作権の相談であり、**AI要約は原文の翻案にあたる**。
原文だけの状態で了解を得ても前提が変わってしまうので、要約まで作ってから一度で相談する。
取得の負荷が理由ではなく、次の2点を確認するため。

1. **リンクの連絡。** 町の[サイト方針](https://www.town.onga.lg.jp/site/userguide/5959.html)が
   「リンク設定を行った場合は、みらいデザイン課 広報係までリンク元のURLをご連絡ください」としている。
2. **著作権の扱い。** 特に**議員ページ**（特定の議員の発言を集めて並べる画面）が、
   著作権法が自由利用から除いている「同一の著作者のものを編集して利用する場合」に当たるかどうか。
   確認が取れるまでは、議員ページは索引に徹する（発言や要約の本文を置かない）。

**連絡文の草案は [議会事務局への連絡_草案.md](議会事務局への連絡_草案.md) にある。**
宛先が2つに分かれる（会議録と著作権は議会事務局、リンクの連絡はみらいデザイン課 広報係）。
リンクの連絡は**公開後**に送るもので、事前相談とは別に扱う。

ついでに聞けるとよいこと:

- 会議録のテキストデータ（HTML以外の形式）があるか。あればパイプラインが一段楽になる。
- 委員会の会議録を公開する予定があるか。
- このサイトの存在を知らせておくことで、後から問い合わせになるのを避けられる。

## 6. 取得マナー（実装済み）

コード側で守っていること。手で実行するときも同じ。

- 1リクエストごとに**3秒以上**あける（`pipeline/common/http.py` の `Fetcher`）。
  1プロセスに1つのフェッチャを使い回すので、並列にはならない。
- `pipeline.fetch.voices` は**日本時間の深夜帯（0〜6時）以外では実行を拒否する**。
  動作確認のときだけ `--limit` と `--allow-daytime` を付ける。
- 取得済みのURLは二度取りに行かない（`state.json`）。
- User-Agent に連絡先URLを入れる。
- 町の公式サイト側は、**索引ページのリンクだけをたどる**。URLの当て推量や総当たりはしない。

初回の一括取得は約500リクエスト・25分前後。2回目以降は数件で終わる。
