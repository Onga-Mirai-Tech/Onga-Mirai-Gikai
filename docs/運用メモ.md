## 1. リポジトリ

| リポジトリ | 公開 | 中身 |
|---|---|---|
| [Onga-Mirai-Gikai](https://github.com/Onga-Mirai-Tech/Onga-Mirai-Gikai) | public | コード・ドキュメント・`masters/`・`state.json` |
| [Onga-Mirai-Gikai-data](https://github.com/Onga-Mirai-Tech/Onga-Mirai-Gikai-data) | **private** | `raw/`・`normalized/`・`summaries/` |

分ける理由は設計ドラフト「3. 全体構成 → リポジトリ構成」を参照。

### deploy key の設定（月次ワークフローに必要）

`.github/workflows/monthly-fetch.yml` が data リポジトリを checkout するために使う。

```bash
# 1. 鍵を作る（パスフレーズなし）
ssh-keygen -t ed25519 -C "onga-mirai-gikai-data-deploy" -f ~/.ssh/onga_data_deploy -N ""

# 2. 公開鍵を data リポジトリの Deploy keys に登録する（書き込みを許可する）
gh repo deploy-key add ~/.ssh/onga_data_deploy.pub \
  --repo Onga-Mirai-Tech/Onga-Mirai-Gikai-data --title "monthly-fetch" --allow-write

# 3. 秘密鍵を コード側リポジトリの Secrets に入れる
gh secret set DATA_REPO_DEPLOY_KEY \
  --repo Onga-Mirai-Tech/Onga-Mirai-Gikai < ~/.ssh/onga_data_deploy
```

秘密鍵はローカルに置いたままにせず、登録後に消してよい。

## 2-1. サブドメインの設定

ドメインもWhois代行も済んでいる。残っているのは**エックスサーバーの管理画面での操作2つ**だけ。

現状（2026-09-22 時点で確認）:

| 項目 | 状態 |
|---|---|
| `onga-mirai-tech.com` | 取得済み。`https://onga-mirai-tech.com/` は 200 で開く |
| `miraigikai.onga-mirai-tech.com` | DNSは引ける（サーバーと同じIPを返す）が、**証明書が `*.xserver.jp` のまま**で https では開けない |

つまり **サブドメインがサーバーパネルに登録されていない**。手順は2つ。

1. **サーバーパネル → 「サブドメイン設定」** で `miraigikai` を追加する
2. **サーバーパネル → 「SSL設定」** で `miraigikai.onga-mirai-tech.com` の無料SSL（Let's Encrypt）を有効にする

反映まで少し時間がかかる。次のコマンドで確認できる。証明書の subject が
`miraigikai.onga-mirai-tech.com` になっていれば完了。

```bash
curl -sS -o /dev/null -w '%{http_code}\n' https://miraigikai.onga-mirai-tech.com/
echo | openssl s_client -servername miraigikai.onga-mirai-tech.com \
  -connect miraigikai.onga-mirai-tech.com:443 2>/dev/null | openssl x509 -noout -subject -dates
```

なお `onga-mirai-tech.com` 本体（親ドメイン）をどう使うかは未決。
みらい議会をサブドメインに置くので、親は空のままでも、別の用途に使ってもよい。

## 3. 連絡先メール

使いどころが3つある。どれも「個人運営の非公式サイト」として矛盾しない形にする。

1. **サイトの問い合わせ先**（フッター・aboutページ）
2. **訂正の受付**（要約や抽出の誤りの指摘）
3. **User-Agent に入れる連絡先** — いまは GitHub リポジトリのURLを入れている（`pipeline/common/http.py`）。町の担当者がアクセスログを見たときに辿れるようにするためのもの。サイト公開後は問い合わせページのURLに差し替えるか検討する

### 迷惑メール対策

`info@` `contact@` `[管理用アドレス]` のような**よくある名前は辞書攻撃の的**になる。
ただしこのサイトはアドレスを公開ページに載せるので、名前を変えるだけでは収集ボットは防げない。
効く順に3つ。

1. **キャッチオールを必ず無効にする。** 存在しないアドレス宛を全部受け取る設定が有効だと、
   辞書攻撃が100%成功してしまう。サーバーパネルで確認する。**いちばん効くのにいちばん見落とされやすい。**
2. **サイトにメールアドレスを載せない。** 問い合わせは Google フォームへのリンクにする。
   リンク先は外部だが、**本サイトのページは「外部読み込みゼロ」を保てる**。
   分割表記（`... [at] ...`）やJSでの組み立ては、収集ボット側が対応済みなので効果が薄い。
3. **名前はサイト名から取る。**

### 使うアドレス

| アドレス | 用途 | 公開 |
|---|---|---|
| `miraigikai@onga-mirai-tech.com` | 問い合わせ・訂正の受付・議会事務局とのやりとり | する |
| （別に1つ用意する） | GitHub・ドメイン・サーバーの管理用 | **しない** |

`miraigikai@` を選ぶ理由:

- 辞書リスト（`info` `contact` `admin` `support` `hello` `mail` `webmaster` …）に入っていない
- サイトのURLが `miraigikai.onga-mirai-tech.com` なので、**受け取った側が一目で本物と分かる**。
  議会事務局とのやりとりでは、この「名乗りとしての信頼性」が要る
- ランダム文字列（`k3f9x@`）は予測されにくいが、公的な連絡先としては怪しく見える

管理用を分けておくと、公開側が迷惑メールで溢れても、アカウント復旧メールなどが埋もれない。
公開側が使い物にならなくなったら、そのアカウントだけ捨てて別の名前に移れる。

エックスサーバーの契約でメールアカウントが作れる。サーバーパネルの「メールアカウント設定」から。
迷惑メールフィルタの設定もあわせて確認する。

**GitHub Issues も窓口として併用できる**が、町民がGitHubアカウントを持っているとは限らないので、
一般向けの窓口の代わりにはならない。技術的な指摘の受け皿として使う。

## 4. X アカウント

デプロイ情報の告知に使う想定。以下に注意する。

- **公式と誤解されない名前にする。** 表示名に「遠賀町議会」だけを置かない。
  プロフィールの1行目に「個人運営の非公式サイトです」と書く。
- 議会に関する発信は、政治的な反応を呼びやすい。**リプライの範囲を絞る**設定を最初から入れておくか決める。
- サイト本体と同じく、**議員・会派・町への評価を書かない**。CLAUDE.md の中立性ルールは
  サイトの外の発信にも及ぶものとして扱う。告知は「更新しました」「この定例会を追加しました」に留める。
- アイコンはロゴC案。ヘッダー画像は反転ロゴ。

## 5. 議会事務局への連絡

**P3（閲覧MVP・原文のみ）の完成時**に行うと決めた（設計ドラフト「10. 未決事項」）。
取得の負荷が理由ではなく、次の2点を確認するため。

1. **リンクの連絡。** 町の[サイト方針](https://www.town.onga.lg.jp/site/userguide/5959.html)が
   「リンク設定を行った場合は、みらいデザイン課 広報係までリンク元のURLをご連絡ください」としている。
2. **著作権の扱い。** 特に**議員ページ**（特定の議員の発言を集めて並べる画面）が、
   著作権法が自由利用から除いている「同一の著作者のものを編集して利用する場合」に当たるかどうか。
   確認が取れるまでは、議員ページは索引に徹する（発言や要約の本文を置かない）。

ついでに聞けるとよいこと:

- 会議録のテキストデータ（HTML以外の形式）があるか。あればパイプラインが一段楽になる。
- 委員会の会議録を公開する予定があるか。
- このサイトの存在を知らせておくことで、後から問い合わせになるのを避けられる。

## 6. 取得マナー（実装済み）

コード側で守っていること。手で実行するときも同じ。

- 1リクエストごとに**3秒以上**あける（`pipeline/common/http.py` の `Fetcher`）。
  1プロセスに1つのフェッチャを使い回すので、並列にはならない。
- `pipeline.fetch.voices` は**日本時間の深夜帯（0〜6時）以外では実行を拒否する**。
  動作確認のときだけ `--limit` と `--allow-daytime` を付ける。
- 取得済みのURLは二度取りに行かない（`state.json`）。
- User-Agent に連絡先URLを入れる。
- 町の公式サイト側は、**索引ページのリンクだけをたどる**。URLの当て推量や総当たりはしない。

初回の一括取得は約500リクエスト・25分前後。2回目以降は数件で終わる。
